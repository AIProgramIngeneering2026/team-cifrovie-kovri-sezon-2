# ADR-0003. Удаление Job — мягкое удаление вне жизненного цикла

- **Дата:** 2026-11-15
- **Статус:** принято

## Контекст и ограничения

В сервисе асинхронного выполнения заданий предусмотрены состояния Job: `created`, `running`, `finished`, `failed` и `cancelled` ([job-lifecycle.md](../job-lifecycle.md)).

Пользователю нужно убирать из списка задания, которые ему больше не нужны. Возник вопрос, следует ли добавлять для этого отдельное состояние `deleted`.

Ограничения:

- жизненный цикл Job должен описывать только выполнение операции и не смешиваться с управлением хранением записи;
- удаление не должно мешать выполнению: воркер не должен встречать удалённую Job;
- ключ идемпотентности не должен освобождаться раньше Job ([ADR-0001](0001-idempotency.md)), иначе повторный запрос создаст дубликат.

## Решение

Удаление Job — не состояние, а отдельная операция `DELETE /api/tasks/{id}`. Диаграмма состояний и переходы не меняются.

Правила:

1. Удалить можно только неактивную Job — в статусе `finished`, `failed` или `cancelled`. Для `created` и `running` сервис возвращает `409` с кодом `task_active`; активную Job сначала отменяют.
2. Удаление мягкое: у Job заполняется время удаления `deleted_at`, статус выполнения и ключ идемпотентности сохраняются.
3. Удалённая Job скрыта от всех чтений через API: её нет в списке, `GET`, `cancel`, `retry` и повторный `DELETE` возвращают `404`.
4. Успешное удаление возвращает `204`. Событие в WebSocket не публикуется, потому что статус не меняется.

## Рассмотренные альтернативы

**A. Добавить состояние `deleted`.** Позволяет явно обозначить удалённые задания, но смешивает жизненный цикл выполнения с управлением данными: последний статус выполнения теряется, появляются переходы `* → deleted` из всех состояний, а каждое чтение и воркер должны помнить про новое состояние. Отвергнуто.

**B. Физическое удаление записи.** Проще в хранении, но вместе с записью удаляется ключ идемпотентности, и повторный запрос с тем же ключом создаст новую Job, что нарушает [ADR-0001](0001-idempotency.md). Также теряется история выполнения. Отвергнуто.

**C. Мягкое удаление отдельной операцией.** Не усложняет диаграмму состояний, сохраняет ключ идемпотентности и историю. Принято.

**D. Не поддерживать удаление.** Самый простой вариант, но список заданий пользователя только растёт. Отвергнуто.

## Цена решения

- Удаление описывается отдельно от переходов между состояниями, API отдельно определяет поведение операции удаления.
- Все чтения заданий должны исключать удалённые записи; эта фильтрация сосредоточена в слое хранения.
- Удалённые записи продолжают занимать место в PostgreSQL.
- Ключ идемпотентности удалённой Job нельзя использовать повторно: клиент получает `409` и должен создать задание с новым ключом.

## Условия пересмотра

Решение пересматривается, если:

- появятся требования к сроку хранения данных и потребуется физически удалять старые записи;
- понадобится восстанавливать удалённые задания;
- потребуется удалять активные задания одной операцией, без предварительной отмены.
