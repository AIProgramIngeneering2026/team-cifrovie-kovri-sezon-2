# ADR-0002. Фоновое выполнение Job через ARQ и Redis

- **Дата:** 2026-11-15
- **Статус:** принято

## Контекст и ограничения

Сервис должен принимать задания от пользователей и выполнять их асинхронно. Некоторые операции могут занимать продолжительное время, поэтому выполнение задания не должно блокировать обработку HTTP-запросов и мешать работе API.

Необходимо обеспечить передачу заданий на выполнение, обработку нескольких заданий, повторные попытки при сбоях воркера и отмену задания пользователем — как ещё не начатого, так и выполняемого.

В проекте используются Python, FastAPI, Redis и PostgreSQL.

## Решение

Для фонового выполнения Job используется ARQ с Redis в качестве очереди заданий.

После получения запроса API создаёт Job в PostgreSQL со статусом `created`, а затем передаёт её на выполнение через ARQ. Воркер получает задание из очереди, переводит его в `running` и запускает соответствующий Tool.

После выполнения Job её статус обновляется в PostgreSQL на `finished` или `failed` в зависимости от результата выполнения.

При аварийном завершении воркера или превышении времени выполнения ARQ повторно запускает задание в пределах настроенного числа попыток. Повторные попытки происходят внутри состояния `running` и не меняют статус. Когда попытки исчерпаны, Job переводится в `failed`, причина сохраняется. Перезапуск Job из `failed` выполняет пользователь действием `retry` ([job-lifecycle.md](../job-lifecycle.md)) — это не автоматический механизм ARQ.

Если при создании Job недоступна PostgreSQL или Redis, API отвечает `503` с кодом `service_unavailable` и заголовком `Retry-After` ([openapi.yaml](../api/openapi.yaml)). Сохранение Job и постановка в очередь выполняются как один шаг: если поставить Job в очередь не удалось, только что созданная запись удаляется. Поэтому после `503` Job не существует, и клиент повторяет запрос с тем же `Idempotency-Key` ([ADR-0001](0001-idempotency.md)) — это создаёт Job заново, а не возвращает «зависшую» в `created`.

Отмена использует прерывание задания в ARQ: Job в `created` не будет запущена воркером, у Job в `running` выполнение Tool прерывается. Статус `cancelled` записывается в PostgreSQL до прерывания, поэтому результат, который Tool успел вернуть, отбрасывается.

## Рассмотренные альтернативы

**A. Синхронное выполнение внутри FastAPI.** API самостоятельно выполняет задание и отправляет ответ только после завершения операции. Отвергнуто, поскольку длительное выполнение может блокировать обработку запросов и приводить к тайм-аутам.

**B. Собственная реализация очереди на Redis.** Позволяет контролировать процесс выполнения заданий, но требует самостоятельно реализовать получение задач, повторные попытки, обработку ошибок и другие механизмы. Отвергнуто из-за дополнительных затрат на разработку и поддержку.

**C. Использование Celery вместо ARQ.** Предоставляет развитые возможности для фонового выполнения и управления очередями, но для текущего масштаба проекта его функциональность избыточна. Отвергнуто в пользу более простого решения.

## Цена решения

- Появляется дополнительная зависимость от Redis.
- Необходимо отдельно запускать и контролировать воркеры ARQ.
- При недоступности Redis новые задания не принимаются: API отвечает `503`, клиент повторяет запрос позже.
- Необходимо учитывать повторное выполнение заданий и предотвращать нежелательные дублирующие побочные эффекты.
- Нужно согласовать параметры retry (число попыток, тайм-аут выполнения) и обработку заданий, которые не удалось выполнить после всех попыток.
- Отмена выполняемого задания срабатывает только в точке, где Tool может быть прерван; Tool должен корректно освобождать ресурсы при прерывании.
- Согласованность PostgreSQL и очереди обеспечена только для ошибки постановки в очередь. Если процесс API аварийно завершится между сохранением Job и постановкой в очередь, Job останется в `created` без сообщения в очереди; этот случай текущее решение не закрывает.

## Условия пересмотра

Решение пересматривается, если:

- ARQ перестанет удовлетворять требованиям проекта по производительности или надёжности;
- потребуется более сложное управление очередями и распределением заданий;
- увеличится нагрузка и возникнет необходимость перейти на другую систему фонового выполнения;
- появятся требования, для которых возможностей ARQ будет недостаточно.
