# ADR-0001. Идемпотентность при создании Job через Idempotency-Key

- **Дата:** 2026-11-15
- **Статус:** принято

## Контекст и ограничения

Клиент отправляет запрос на создание Job. Из-за проблем с сетью, тайм-аута или повторной отправки один и тот же запрос может поступить в систему несколько раз.

Без защиты от повторных запросов система может создать несколько одинаковых заданий, что приведёт к повторному выполнению одной операции и нежелательным побочным эффектам.

Сервис должен гарантировать, что повторная отправка запроса с одним и тем же ключом идемпотентности не создаёт новую Job.

Все запросы к API выполняются от имени аутентифицированного пользователя (JWT в cookie или API-ключ), поэтому ключи разных пользователей не должны влиять друг на друга.

Решение касается только создания Job. Повторное выполнение Job — автоматические попытки ARQ и действие пользователя `retry` — описано в [job-lifecycle.md](../job-lifecycle.md) и [ADR-0002](0002-background-worker.md).

## Решение

Для защиты от дублирования при создании Job используется ключ идемпотентности `Idempotency-Key`, который передаётся клиентом при отправке запроса.

Ключ сохраняется в PostgreSQL вместе с созданной Job. Уникальность обеспечивается ограничением на пару `(user_id, idempotency_key)`: один и тот же ключ у разных пользователей не конфликтует.

Правила обработки запросов:

1. При получении запроса система проверяет наличие `Idempotency-Key`.
2. Если ключ ранее не использовался этим пользователем, создаётся новая Job, а ключ сохраняется вместе с ней.
3. Если у пользователя уже есть Job с этим ключом, новая Job не создаётся. Система возвращает существующую Job с её актуальными данными, в том числе текущим статусом.
4. Повторный запрос с тем же ключом не запускает Job повторно и не меняет её состояние.
5. Если Job с этим ключом удалена ([ADR-0003](0003-job-deletion.md)), ключ остаётся занятым: система возвращает `409` с кодом `idempotency_key_used` и не создаёт новую Job. Удалённая Job не возвращается, потому что для пользователя её больше нет.

Планировщик создаёт Job по расписанию через тот же механизм с ключом «расписание + время срабатывания», поэтому одно срабатывание не порождает две Job.

## Рассмотренные альтернативы

**A. Не использовать ключ идемпотентности.** Каждый запрос создаёт новую Job. Отвергнуто, поскольку повторная отправка запроса может привести к созданию нескольких одинаковых заданий.

**B. Хранить ключи только в Redis.** Это позволяет быстро проверять наличие ключа, но при потере данных Redis или истечении срока хранения может возникнуть повторное создание Job. Кроме того, проверка ключа и сохранение задания должны быть согласованы. Отвергнуто в пользу хранения ключа непосредственно в PostgreSQL.

**C. Проверять дубликаты по содержимому запроса.** Система могла бы сравнивать параметры заданий и не создавать одинаковые Job. Отвергнуто, поскольку пользователь может намеренно создать два задания с одинаковыми параметрами. Ключ позволяет клиенту самостоятельно определять, является ли запрос повторным.

**D. Глобальная уникальность ключа.** Проще в реализации, но ключ одного пользователя блокирует такой же ключ другого, а ответ на повтор может раскрыть чужую Job. Отвергнуто в пользу уникальности в пределах пользователя.

## Цена решения

- Клиент должен передавать ключ идемпотентности при создании Job.
- Необходимо хранить ключ вместе с заданием и обеспечивать уникальность пары `(user_id, idempotency_key)` на уровне базы данных.
- Ключи не должны удаляться раньше связанных с ними Job, иначе повторный запрос сможет создать дубликат. Поэтому удаление Job мягкое ([ADR-0003](0003-job-deletion.md)), а ключ удалённой Job остаётся занятым.
- При повторном запросе возвращается актуальное состояние Job, которое может отличаться от состояния на момент первого запроса.
- Идемпотентность защищает от повторного создания Job, но сама по себе не гарантирует отсутствие повторных побочных эффектов при повторном выполнении. Исполнение Tool также должно учитывать возможность повторного запуска.

## Условия пересмотра

Решение пересматривается, если:

- появится необходимость ограничивать срок хранения ключей;
- потребуется использовать отдельное хранилище ключей идемпотентности;
- появится общий для нескольких пользователей доступ к Job (команды, организации) и ключи нужно будет разделять иначе, чем по пользователю.
