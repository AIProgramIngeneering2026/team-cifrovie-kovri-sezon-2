# Требования

Сервис асинхронного выполнения заданий (Job) позволяет пользователю
запускать длительные операции в фоновом режиме, настраивать их запуск по
расписанию, отслеживать состояние выполнения и получать сохранённые
результаты.

## Участники

- **Аутентифицированный пользователь** --- создаёт задания и
  расписания, просматривает список заданий и результаты, отменяет
  задания и получает уведомления об изменении статуса через WebSocket.
- **Воркер (ARQ)** --- забирает задания из очереди, находит
  исполнителя (Tool) по типу операции и выполняет его.
- **Планировщик** --- проверяет активные расписания и при наступлении
  заданного времени создаёт обычное задание (Job).

## Сценарии

### Сценарий 1. Создание задания (asleep)

**Цель:** пользователь создаёт задание типа `asleep`, которое
выполняется в фоновом режиме, и получает его идентификатор для
отслеживания.

**Участник:** аутентифицированный пользователь.

**Основной поток:**

1.  Пользователь проходит аутентификацию по email с помощью OTP и
    получает токены в cookie.
2.  Пользователь отправляет `POST /api/tasks` с телом
    `{"name": "pause", "type": "asleep", "seconds": 10}`.
3.  Сервис проверяет параметры и сохраняет задание в PostgreSQL со
    статусом `CREATED`.
4.  Сервис ставит задание в очередь ARQ (Redis), учитывая ключ
    идемпотентности.
5.  Сервис возвращает идентификатор задания и его статус `CREATED`.

**Критерии приёмки (ДАНО / КОГДА / ТОГДА):**

- **ДАНО** пользователь аутентифицирован; **КОГДА** он отправляет
  запрос на создание задания типа `asleep` с корректными параметрами;
  **ТОГДА** сервис возвращает HTTP `201`, идентификатор задания,
  статус `CREATED` и время создания.
- **ДАНО** задание создано со статусом `CREATED`; **КОГДА** воркер
  забирает его из очереди; **ТОГДА** статус меняется на `IN_PROGRESS`,
  а после успешного выполнения --- на `FINISHED`.
- **ДАНО** пользователь уже создал задание с определённым ключом
  идемпотентности; **КОГДА** он повторно отправляет запрос с тем же
  ключом; **ТОГДА** сервис возвращает идентификатор ранее созданного
  задания и не создаёт дубликат.

### Сценарий 2. Получение списка заданий и информации о задании

**Цель:** пользователь просматривает свои задания и получает подробную
информацию о конкретном задании, включая результат выполнения.

**Участник:** аутентифицированный пользователь.

**Основной поток:**

1.  Пользователь отправляет `GET /api/tasks` с токеном аутентификации в
    cookie.
2.  Сервис возвращает список заданий этого пользователя: идентификатор,
    название, тип, статус, время создания и результат, если он доступен.
3.  Пользователь отправляет `GET /api/tasks/{id}`, чтобы получить
    подробную информацию о задании.
4.  Сервис возвращает данные задания, включая результат выполнения или
    сведения об ошибке.

**Критерии приёмки (ДАНО / КОГДА / ТОГДА):**

- **ДАНО** у пользователя есть несколько заданий; **КОГДА** он
  запрашивает список; **ТОГДА** сервис возвращает только его задания,
  отсортированные по времени создания от новых к старым.
- **ДАНО** запрашивается задание с несуществующим идентификатором;
  **КОГДА** вызывается `GET /api/tasks/{id}`; **ТОГДА** сервис
  возвращает HTTP `404`.
- **ДАНО** задание завершено со статусом `FINISHED`; **КОГДА**
  пользователь запрашивает его подробную информацию; **ТОГДА** ответ
  содержит поле `result` с данными исполнителя.

### Сценарий 3. Получение обновлений статуса через WebSocket

**Цель:** пользователь отслеживает изменение статуса задания без
необходимости вручную обновлять страницу.

**Участник:** аутентифицированный пользователь с открытым
WebSocket-соединением.

**Основной поток:**

1.  Пользователь устанавливает WebSocket-соединение `WS /api/tasks/ws` с
    использованием предусмотренного механизмом аутентификации токена.
2.  Сервис подтверждает соединение приветственным сообщением.
3.  Воркер изменяет статус задания.
4.  Сервис публикует событие об изменении статуса в Redis Pub/Sub, канал
    `task_status_updates`.
5.  Слушатель событий отправляет уведомление пользователю через
    WebSocket.
6.  Клиент обновляет статус задания в интерфейсе.

**Критерии приёмки (ДАНО / КОГДА / ТОГДА):**

- **ДАНО** у пользователя открыто WebSocket-соединение; **КОГДА**
  изменяется статус его задания; **ТОГДА** пользователь получает
  сообщение с новым статусом в течение одной секунды.
- **ДАНО** пользователь не аутентифицирован; **КОГДА** он пытается
  установить WebSocket-соединение; **ТОГДА** сервис отклоняет
  подключение.
- **ДАНО** WebSocket-соединение пользователя закрыто; **КОГДА**
  изменяется статус его задания; **ТОГДА** сервер не пытается
  отправить сообщение в закрытое соединение и корректно обрабатывает
  отсутствие получателя.

### Сценарий 4. Отмена задания

**Цель:** пользователь отменяет задание, которое ещё не началось или уже
выполняется.

**Участник:** аутентифицированный пользователь.

**Основной поток:**

1.  Пользователь создаёт задание, например типа `asleep`.
2.  Пользователь отправляет запрос на отмену задания через
    `POST /api/tasks/{id}/cancel`.
3.  Сервис проверяет, что задание принадлежит пользователю и имеет
    статус `CREATED` или `IN_PROGRESS`.
4.  Сервис переводит задание в статус `CANCELLED`. Если задание ещё не
    выполняется, сервис предотвращает его запуск; если выполняется ---
    передаёт сигнал отмены исполнителю.
5.  Сервис публикует изменение статуса через Redis Pub/Sub и отправляет
    уведомление по WebSocket.
6.  Сервис возвращает подтверждение отмены.

**Критерии приёмки (ДАНО / КОГДА / ТОГДА):**

- **ДАНО** задание имеет статус `CREATED`; **КОГДА** пользователь
  отменяет его; **ТОГДА** статус меняется на `CANCELLED`, и задание не
  начинает выполняться.
- **ДАНО** задание имеет статус `IN_PROGRESS`; **КОГДА** пользователь
  отменяет его; **ТОГДА** сервис инициирует отмену, а исполнитель
  прекращает работу при ближайшей предусмотренной точке проверки
  отмены.
- **ДАНО** задание имеет терминальный статус `FINISHED`, `FAILED` или
  `CANCELLED`; **КОГДА** пользователь пытается его отменить; **ТОГДА**
  сервис возвращает HTTP `409`.
- **ДАНО** задание принадлежит другому пользователю; **КОГДА** текущий
  пользователь пытается его отменить; **ТОГДА** сервис не раскрывает
  данные чужого задания и возвращает ответ, предусмотренный политикой
  доступа.

### Сценарий 5. Выполнение задания типа fetch

**Цель:** пользователь запускает задание типа `fetch`, которое выполняет
запросы к нескольким URL и формирует общий результат.

**Участник:** аутентифицированный пользователь.

**Основной поток:**

1.  Пользователь создаёт задание типа `fetch`, передавая список URL.
2.  Сервис создаёт задание со статусом `CREATED` и ставит его в очередь.
3.  Воркер запускает исполнитель `fetch`, который выполняет запросы к
    URL параллельно, с таймаутом и ограниченным количеством повторов.
4.  Если отдельный URL недоступен, ошибка фиксируется в соответствующей
    части результата, но не приводит к сбою всего задания.
5.  После завершения исполнитель сохраняет агрегированный результат, а
    задание переходит в `FINISHED`.
6.  Пользователь получает результат через `GET /api/tasks/{id}`.

**Критерии приёмки (ДАНО / КОГДА / ТОГДА):**

- **ДАНО** в списке URL есть недоступный адрес, а остальные адреса
  доступны; **КОГДА** выполняется задание `fetch`; **ТОГДА** задание
  завершается со статусом `FINISHED`, а результат содержит успешные
  ответы и информацию об ошибке для недоступного адреса.
- **ДАНО** все запросы завершились ошибками, но исполнитель смог
  обработать их и сформировать результат; **КОГДА** выполнение задания
  заканчивается; **ТОГДА** задание переходит в `FINISHED`, а результат
  содержит ошибки по всем URL.
- **ДАНО** исполнитель не смог завершить работу из-за внутренней
  ошибки или нарушения обязательных условий выполнения; **КОГДА**
  выполнение задания прекращается; **ТОГДА** задание переходит в
  `FAILED`, а причина ошибки сохраняется.
- **ДАНО** задание завершено со статусом `FINISHED`; **КОГДА**
  пользователь запрашивает его подробную информацию; **ТОГДА** ответ
  содержит поле `result` со списком результатов по каждому URL.

## Ошибочные сценарии

### Ошибка 1. Неверный или просроченный OTP-код

**Участник:** пользователь, пытающийся пройти аутентификацию.

**Описание:**

1.  Пользователь запрашивает OTP-код на свой email.
2.  Пользователь отправляет неверный код или код, срок действия которого
    истёк.
3.  Сервис не выдаёт токены и возвращает ошибку.
4.  Пользователь может запросить новый код и повторить попытку.

**Критерии приёмки:**

- **ДАНО** введён неверный OTP-код; **КОГДА** вызывается
  `POST /api/auth/validate-otp`; **ТОГДА** сервис возвращает HTTP
  `401`, токены не выдаются.
- **ДАНО** срок действия OTP-кода истёк; **КОГДА** пользователь
  отправляет этот код; **ТОГДА** сервис возвращает HTTP `401` и не
  выдаёт токены.

### Ошибка 2. Создание задания с некорректными параметрами

**Участник:** аутентифицированный пользователь.

**Описание:**

1.  Пользователь отправляет запрос на создание задания с некорректными
    параметрами: например, с неположительным количеством секунд для
    `asleep`, невалидным списком URL для `fetch` или неподдерживаемым
    типом операции.
2.  Сервис проверяет параметры на уровне схемы и бизнес-логики.
3.  Сервис возвращает ошибку с описанием причины. Задание не сохраняется
    и не попадает в очередь.

**Критерии приёмки:**

- **ДАНО** для `asleep` указано `seconds <= 0`; **КОГДА** вызывается
  `POST /api/tasks`; **ТОГДА** сервис возвращает HTTP `422`, а задание
  не создаётся.
- **ДАНО** указан неподдерживаемый тип операции; **КОГДА**
  пользователь отправляет запрос на создание задания; **ТОГДА** сервис
  возвращает ошибку валидации, а задание не создаётся.

### Ошибка 3. Аварийное завершение воркера во время выполнения задания

**Участник:** воркер (ARQ), планировщик и аутентифицированный пользователь.

**Описание:**

1. Воркер забирает задание из очереди, и его статус меняется на `IN_PROGRESS`.
2. Во время выполнения воркер аварийно завершается или превышает установленное время выполнения.
3. Система обнаруживает сбой и учитывает количество попыток выполнения задания.
4. Если остались попытки, ARQ повторно запускает задание.
5. Если количество попыток исчерпано, задание переводится в `FAILED`, а причина ошибки сохраняется.

**Критерии приёмки (ДАНО / КОГДА / ТОГДА):**

- **ДАНО** задание находится в статусе `IN_PROGRESS`; **КОГДА** воркер аварийно завершается; **ТОГДА** система обнаруживает незавершённое выполнение и обрабатывает его согласно политике повторных попыток.
- **ДАНО** для задания остались доступные попытки; **КОГДА** происходит временный сбой выполнения; **ТОГДА** ARQ повторно запускает задание.
- **ДАНО** количество попыток выполнения исчерпано; **КОГДА** очередная попытка завершается неудачей; **ТОГДА** задание переводится в `FAILED`, а причина ошибки сохраняется.
- **ДАНО** задание запускается повторно; **КОГДА** исполнитель выполняет операцию; **ТОГДА** повторный запуск не приводит к некорректному дублированию побочных эффектов.

## Жизненный цикл Job

### Состояния

- **CREATED** --- задание создано, сохранено в PostgreSQL и поставлено
  в очередь ARQ (Redis), но ещё не взято воркером в работу.
- **IN_PROGRESS** --- воркер забрал задание из очереди, выбрал
  исполнителя (Tool) и выполняет операцию.
- **FINISHED** --- задание успешно завершено, результат исполнителя
  сохранён. Терминальное состояние.
- **FAILED** --- выполнение завершилось ошибкой, из-за которой
  исполнитель не смог завершить операцию. Причина ошибки сохранена.
  Терминальное состояние.
- **CANCELLED** --- задание отменено пользователем до начала или во
  время выполнения. Терминальное состояние.

### Разрешённые переходы

- `CREATED → IN_PROGRESS`
- `CREATED → CANCELLED`
- `CREATED → FAILED`
- `IN_PROGRESS → FINISHED`
- `IN_PROGRESS → FAILED`
- `IN_PROGRESS → CANCELLED`

У состояний `FINISHED`, `FAILED` и `CANCELLED` нет исходящих переходов:
они являются терминальными.

### Диаграмма переходов

```text
                 ┌──────────────→ FINISHED
                 │
CREATED → IN_PROGRESS
   │             │
   │             └──────────────→ FAILED
   │
   ├────────────→ CANCELLED
   │
   └────────────→ FAILED

FINISHED, FAILED, CANCELLED — терминальные состояния.
```

Каждое изменение статуса публикуется в Redis Pub/Sub, канал
`task_status_updates`, и при наличии активного соединения доставляется
пользователю через WebSocket.

## Что предложил ИИ

Для поиска дополнительных способов нарушения основного сценария
использовался следующий промпт:

> Проанализируй сценарии сервиса асинхронного выполнения заданий.
> Предложи три дополнительных способа, которыми основной
> пользовательский сценарий может завершиться некорректно. Для каждого
> способа опиши условие возникновения, возможные последствия и критерий
> приёмки, который позволит проверить корректное поведение системы.

### Предложение 1. Повторное создание задания при повторной обработке срабатывания расписания

**Ситуация:** планировщик может повторно обработать одно и то же
срабатывание расписания, например после перезапуска или временного сбоя.
В результате могут появиться несколько одинаковых заданий.

**Решение:** принято. Для одного срабатывания расписания должно
создаваться не более одного задания. Это требование добавлено в критерии
приёмки сценария 5.

### Предложение 2. Доступ пользователя к чужому заданию

**Ситуация:** пользователь может попытаться получить или отменить
задание другого пользователя, подставив его идентификатор в API-запрос.

**Решение:** принято. Сервис должен проверять принадлежность задания
текущему пользователю при получении подробной информации и отмене.
Проверка доступа добавлена в критерии сценария 4; аналогичную проверку
необходимо учитывать при реализации сценария 2.

### Предложение 3. Потеря уведомления при разрыве WebSocket-соединения

**Ситуация:** соединение пользователя может быть закрыто в момент
изменения статуса. Пользователь не получит уведомление и может увидеть
устаревший статус.

**Решение:** принято частично. Сервер не должен пытаться отправлять
сообщения в закрытое соединение. При повторном подключении клиент может
запросить актуальное состояние задания через `GET /api/tasks/{id}`. Это
поведение опирается на сценарии 2 и 3; отдельный механизм
гарантированной доставки уведомлений не включается в текущие требования.
