# Сервис асинхронного выполнения заданий

Командный проект cifrovie-kovri-sezon-2 по дисциплине «Программная инженерия».

## Проблема и пользователи

Многие операции нельзя выполнить за время одного HTTP-запроса: опрос нескольких внешних API, отправка писем,
длительные вычисления. Если выполнять их синхронно, клиент ждёт ответа, соединение обрывается по таймауту,
а при повторной отправке запроса работа выполняется дважды. Пользователю при этом не видно, на каком этапе находится
операция и чем она закончилась.

Сервис предназначен для разработчиков и пользователей внутренних инструментов, которым нужно поставить длительную
операцию в очередь, следить за её статусом в реальном времени и получить сохранённый результат. Сервис отвечает
за надёжное выполнение и прозрачный жизненный цикл задания, но не за смысл данных, которые возвращают внешние ресурсы.

## Как работает сервис

1. Пользователь входит по email: сервис отправляет одноразовый код (OTP), после подтверждения выдаёт токены в cookie.
2. Пользователь через Client/API создаёт задание (Job): указывает название, тип операции, её параметры и ключ идемпотентности.
3. Сервис проверяет параметры, сохраняет задание в БД со статусом `created`, ставит его в очередь и возвращает идентификатор.
4. Воркер забирает задание из очереди, находит исполнителя (Tool) по типу операции в реестре и выполняет его.
5. Каждое изменение статуса публикуется в Redis Pub/Sub и доставляется клиенту по WebSocket.
6. Пользователь получает список своих заданий, статус и результат конкретного задания через API.

Тип операции — заранее зарегистрированный исполнитель с единым контрактом: принимает проверенные параметры,
возвращает результат или описание ошибки. Встроенные исполнители:

- `asleep` — ожидание заданного числа секунд (эталонная длительная операция для проверки очереди, статусов и отмены);
- `fetch` — параллельный запрос списка URL и сбор ответов (внешняя зависимость по сети);
- `file_checksum` — скачивание файла по URL с ограничением размера и подсчёт его SHA-256 (длительная операция
  с потоковой загрузкой, которую можно отменить в процессе);
- `page_digest` — загрузка веб-страницы и извлечение сводки: заголовок, мета-описание, язык, число слов и ссылок.

Результат задания содержит итоговый статус, время создания и завершения, данные исполнителя или единообразно
оформленную ошибку. Если один из URL в `fetch` недоступен, это часть результата, а не сбой всего задания;
задание переходит в `failed`, только если исполнитель не смог отработать: например, файл в `file_checksum` превысил
допустимый размер или загрузка оборвалась, а ответ для `page_digest` оказался не HTML-страницей.

## Технологии

- Python 3.14, FastAPI (асинхронный API, OpenAPI-контракт);
- ARQ + Redis — очередь заданий и Pub/Sub для событий статуса;
- PostgreSQL + SQLAlchemy (async) + Alembic — хранение заданий и результатов, миграции;
- httpx — HTTP-клиент для внешних запросов;
- uv, Ruff, basedpyright, pytest — зависимости, линтер, проверка типов, тесты;
- Docker Compose — запуск приложения и зависимостей.

## Границы первой версии

В систему входят:

- аутентификация по email с одноразовым кодом и JWT в cookie;
- создание задания, получение списка заданий, статуса и результата через сетевой API;
- возможность альтернативного использования API через API ключ
- идемпотентное создание задания по ключу из заголовка запроса;
- жизненный цикл задания с проверкой допустимых переходов, включая ошибку и отмену;
- не меньше трёх исполнителей за единым контрактом; новый добавляется регистрацией без правки диспетчера;
- обращение к внешним HTTP-ресурсам через адаптер с timeout, ограниченным retry и разбором некорректного ответа;
- уведомления об изменении статуса по WebSocket;
- хранение заданий и результатов в PostgreSQL с миграциями;
- автоматические тесты, CI, структурированные логи с correlation ID и health check;
- запуск приложения и зависимостей одной командой по инструкции.

За границами первой версии:

- выполнение произвольного пользовательского кода или shell-команд;
- планирование заданий по расписанию (cron) и цепочки зависимых заданий;
- роли, права администратора, квоты и тарификация;
- полноценный веб-интерфейс (демонстрационная страница не оценивается и не развивается);
- облачный деплой, горизонтальное масштабирование и брокеры сообщений помимо Redis;
- хранение результатов дольше заданного срока и выгрузка во внешние хранилища.

## Подключение LLM во втором семестре

Планируется отдельный компонент с возможностью ввода команд для LLM. LLM получит возможность создавать подробные
отчеты, ставить задачи в очередь. Исполнитель `page_digest`: детерминированное извлечение сводки страницы можно заменить на краткое
содержание, сформированное LLM, без изменения контракта Tool и диспетчера.

Параметры, предложенные LLM, проходят ту же валидацию, что и ручной ввод. Ошибка или недоступность LLM не должна
приводить к созданию задания с некорректными параметрами — пользователь получает отказ и может указать операцию вручную.
