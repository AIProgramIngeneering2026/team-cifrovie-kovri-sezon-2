# Правила совместной разработки

Документ описывает порядок работы команды над проектом «Сервис асинхронного выполнения заданий». Правила обсуждаются
участниками команды в Pull Request, предложения и замечания фиксируются в комментариях. Для утверждения правил
требуется одобрение (Approve) другого участника команды. После объединения Pull Request с веткой `main` правила
считаются принятыми.

## 1. Задачи (GitHub Issues)

- Перед началом работы создаём GitHub Issue: название, описание, ожидаемый результат, исполнитель (Assignees).
- Если задача связана с пользовательским сценарием, указываем сценарий и критерии приёмки из `docs/requirements.md`.
- Метки: `scenario` — реализация сценария, `infra` — инфраструктура (CI, Docker, миграции), `docs` — документация,
  `bug` — ошибка.
- В Pull Request добавляем ссылку на Issue с ключевым словом закрытия, например `Closes #12`.
- Изменения, затрагивающие общие контракты — состояния Job, контракт Tool, формат ошибок API, схему БД, — заранее
  обсуждаем в Issue с другим участником.

## 2. Ветки

- `main` — основная ветка с согласованными изменениями. Прямые push и force push в `main` запрещены.
- Для каждой задачи создаём отдельную ветку от актуальной `main`.
- Имя ветки: `<тип>/<номер-issue>-<краткое-описание>` латиницей через дефис:
    - `docs/3-contributing` — документация;
    - `docs/5-scenario-create-job` — описание сценария;
    - `feat/8-job-dispatcher` — новая функциональность;
    - `fix/11-duplicate-idempotency-key` — исправление ошибки;
    - `test/12-job-transitions` — тесты;
    - `chore/13-ci-ruff` — инфраструктура и настройки.
- Несвязанные изменения выполняем в разных ветках и PR. Перед открытием PR обновляем ветку от актуальной `main`
  (`git rebase main` или `git merge main`) и разрешаем конфликты у себя.

## 3. Коммиты

- Один коммит — одно законченное, логически связанное изменение.
- Формат сообщения: `<тип>: <что сделано>` на русском языке, в повелительном наклонении:
    - `docs: описать сценарий создания задания`;
    - `feat: добавить реестр исполнителей`;
    - `fix: отклонять переход из done в running`;
    - `test: проверить идемпотентное создание задания`;
    - `chore: настроить ruff и basedpyright в CI`.
- Типы: `feat`, `fix`, `docs`, `test`, `refactor`, `chore`.
- Не используем сообщения вида `fix`, `update`, `правки`, `wip`.
- Не смешиваем в одном коммите новую функцию, постороннее форматирование и исправление другой ошибки.
- Секреты, `.env`, токены и пароли в коммиты не попадают; пример конфигурации — только в `.env.example`.

## 4. Pull Request

1. Автор завершает согласованную часть задачи в своей ветке.
2. Для кода локально проходит цепочку проверок:
   `uv run ruff check`, `uv run basedpyright`, `uv run pytest`.
3. Создаёт PR в `main` и указывает в описании:
    - связанную Issue;
    - что изменено и зачем;
    - как проверено изменение и какие ограничения остались.
4. Назначает проверяющим другого участника команды в Reviewers. Автор не одобряет собственный PR.
5. Исправляет существенные замечания; после значимых изменений повторно запрашивает review.
6. Объединяет PR в `main` (Squash and merge или Merge commit) только после одобрения другого участника и успешных
   обязательных автоматических проверок, если они настроены. Ветку после слияния удаляем.

## 5. Code Review

- В команде два участника, поэтому каждый проверяет PR другого. Если проверяющий недоступен дольше двух дней,
  договариваемся в командном чате о сроках, но без approve PR не вливается.
- Проверяющий сначала читает Issue и описание PR, затем изменённые файлы (`Files changed`).
- Проверяем: соответствие задаче и критериям приёмки; корректность переходов состояний Job; обработку ошибок и
  граничных случаев; соблюдение слоёв (`endpoints → services → repositories → infrastructure`); наличие тестов;
  согласованность терминов и контрактов; обновление документации.
- При проверке документации убеждаемся, что обязательные разделы присутствуют, требования однозначны, критерии
  приёмки проверяемы, а `README.md`, сценарии и жизненный цикл Job не противоречат друг другу.
- Review содержит хотя бы одно содержательное замечание, предложение или вопрос по сути. Формального `LGTM`
  недостаточно.
- Используем режимы GitHub: `Comment` — вопрос или пожелание, `Request changes` — блокирующее замечание,
  `Approve` — изменение можно вливать.
- Автор отвечает на каждое замечание и вносит согласованные исправления. Нерешённые существенные вопросы блокируют
  объединение PR.

## 6. Definition of Done (критерии готовности)

Задача считается завершённой, если:

- выполнена цель Issue и проверены соответствующие критерии приёмки;
- изменения согласованы с требованиями, жизненным циклом Job и контрактами компонентов;
- для кода: добавлены или обновлены тесты, включая негативные; `ruff`, `basedpyright` и `pytest` проходят;
- для изменений схемы БД: добавлена миграция Alembic, она применяется на чистой базе;
- для документации: проверены структура, ссылки и согласованность формулировок с другими документами;
- обязательные автоматические проверки в CI пройдены (если настроены);
- создан PR со ссылкой на Issue и описанием способа проверки;
- получено одобрение другого участника, существенные замечания устранены;
- PR объединён с `main`, Issue закрыта.

## 7. Учёт личного вклада

- Каждый участник сохраняет полные ссылки на свои влитые PR и PR, в которых выполнил содержательное review.
- При подготовке отчёта `pN.md` команда указывает эти ссылки в разделе «Вклад участников».
- В каждой практике участник подтверждает вклад собственным влитым PR или содержательным review чужого PR;
  по возможности — и тем и другим.
- Один и тот же PR засчитывается участнику как подтверждение вклада только в одной практике.

## 8. Использование ИИ

ИИ можно использовать как вспомогательный инструмент. Автор обязан проверить предложенное решение, исправить ошибки
и уметь объяснить результат на review.
